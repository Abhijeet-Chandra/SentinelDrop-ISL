# Cloud deployment

This setup hosts the React/Vite frontend on Vercel and the FastAPI backend on Render. SQLite stores accounts, audit records, trusted-device approvals, session authorization, replay nonce reservations, and queued ciphertext. Keep one backend instance when using SQLite; multiple instances require a shared database and compatible coordination.

## Before deploying

- Publish this repository to GitHub from GitHub Desktop.
- Create a Vercel account and a Render account.
- The Render Blueprint uses the Free plan. Its SQLite database, generated identity keys, received files, and Vosk model are stored on ephemeral storage and can be lost on restart, spin-down, or redeploy. Use a paid service with a persistent disk before relying on stored data.

This remains a small single-instance demo deployment. Render disks cannot be shared between multiple service instances. The browser-held identity private key is stored in IndexedDB; losing or clearing browser site data loses that identity and requires re-pairing. Keep backups of the persistent database and audit signing key. A free Render instance has ephemeral storage: its database, accounts, trusted devices, audit history, and queued messages can disappear after restart, spin-down, or redeploy. Do not treat ephemeral deployment storage as a backup. This student project has not had an independent security review.

The deployed Admin dashboard's **Live API request monitor** works without TShark. It counts only requests handled by this FastAPI process during a bounded window; its byte totals come from Content-Length headers and are not packet or network-byte measurements. The separate TShark packet-capture control still needs a host with TShark and capture permissions, and may be unavailable on Render. Both monitors lose their in-memory run state when the process restarts.

## 1. Deploy the frontend on Vercel

1. Import the GitHub repository into Vercel.
2. Set **Root Directory** to `frontend`.
3. Use the Vite defaults: build command `npm run build`, output directory `dist`.
4. Deploy once to obtain the frontend's production URL. API calls will not work until the backend URL is configured below.

The included `frontend/vercel.json` routes browser page requests to the SPA entry point.

## 2. Deploy the backend on Render

1. In Render, create a **Blueprint** from the same GitHub repository. Render reads `render.yaml` from the repository root.
2. When prompted for `SENTINEL_ALLOWED_ORIGINS`, enter the exact Vercel production origin, for example `https://your-app.vercel.app` (no path or trailing slash).
3. Confirm the Free plan and its ephemeral storage before applying the Blueprint. The API is public on its Render URL; keep `SENTINEL_RATE_LIMIT_DISABLED` set to `0` and leave encryption demo logging disabled.
4. Wait for the service health check at `/health` to pass. Copy the backend's `https://...onrender.com` URL.

## 3. Connect the frontend to the API

In Vercel, open the frontend project's environment variables and set:

```text
VITE_API_BASE_URL=https://your-api.onrender.com
```

Do not add a trailing slash. Redeploy the frontend so Vite includes the value in its production build.

If you use Vercel Preview deployments, add each preview origin you want to use to Render's `SENTINEL_ALLOWED_ORIGINS`, comma-separated. Use only origins you control.

## Administrator login and audit records

In the Render service's **Environment** settings, set both `SENTINEL_ADMIN_USERNAME` and `SENTINEL_ADMIN_PASSWORD`. Keep the password in Render's secret environment variable field; do not commit it to GitHub. Use a strong password no longer than 72 UTF-8 bytes. The service creates or updates this administrator account at startup. Admin accounts cannot be self-registered, and the Admin login endpoint rejects ordinary users.

The audit API and message-log API require an admin account on the server, not just an admin-looking frontend. Ordinary user sessions cannot fetch the audit log or ciphertext log endpoints. Message records contain sender/recipient, sent/received timestamps, ciphertext, its SHA-256 digest, nonce, AES-GCM authentication tag, and a server-generated Ed25519 audit attestation. This attestation is signed by the server; it is not a digital signature generated by the sender's device. Plaintext is not stored in these message records.

The Admin Dashboard's **Configuration readiness** card checks whether the admin bootstrap variables and CORS list are set, whether the readiness request used HTTPS, whether SQLite is under the configured writable data directory, and whether the Vosk model files are present. These are configuration signals only: they cannot prove that Render retains the disk through redeploys, that hosting settings are active, or that two physical devices can communicate. The same Admin area offers bounded live capture only when the backend has TShark and appropriate interface permissions.

Ordinary voice notes use Vosk WebAssembly in the sender's browser. On first use, the authenticated `/voice/model` route may download the model from Alpha Cephei and prepare a gzipped archive; the backend therefore needs outbound internet access and writable model storage for initial setup. The browser saves the archive in IndexedDB and performs later transcription locally, including while offline. Clearing browser site data requires downloading the model again. Only audio size and transcription duration are sent to the API for the Admin timing chart; WAV data is uploaded only when an Admin deliberately selects a sample for the separate benchmark.

If the account is using a free service with ephemeral storage, the SQLite users, audit logs, message records, browser-pair approvals, and audit signing key can be lost on redeploy, restart, or spin-down. The admin account is recreated from the two environment variables at startup, but old records cannot be recovered after the database is lost. In the Render environment dashboard, verify the selected plan and persistent disk rather than relying only on the configuration card.

## Local development

Leave `VITE_API_BASE_URL` unset locally. Vite will continue proxying API calls to `http://127.0.0.1:8000`.
